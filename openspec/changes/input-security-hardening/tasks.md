## 2. Límite de tasa por chat_id — capability `bot-rate-limiting`

> Requiere OK explícito del usuario para este grupo. Cuotas fijadas en 0.2. Toca `codigo.json`.

- [x] 2.1 Esquema de claves implementado tal como estaba diseñado: `ratelimit:<chat_id>:<bucket>:<ventana>`, `bucket` ∈ {`msg`, `file`}. `<ventana>` = `'m-' + Math.floor(Date.now()/60000)` (ventana corta, 1 min) o `'h-' + Math.floor(Date.now()/3600000)` (ventana larga, 1 h) — prefijo `m-`/`h-` agregado para que ambas ventanas nunca colisionen numéricamente y sean legibles en Redis. Un evento de archivo toca 4 claves (`msg` corta/larga + `file` corta/larga); un mensaje de texto/callback toca 2 (`msg` corta/larga). Clave auxiliar de aviso único: `ratelimit:<chat_id>:notified:<ventana>`, donde `<ventana>` es la del bucket/ventana que efectivamente disparó el exceso (corta si corta se excedió, si no larga).
- [x] 2.2 Insertado el nodo Code `Clasificar evento para rate limit` **inmediatamente después de `Telegram Trigger`, ANTES de `Code in JavaScript7`** (no antes de `Code in JavaScript5` como decía el texto original de esta tarea — ver "Punto de empalme" en el reporte de apply de grupo 2: se verificó por script que el nodo real aguas abajo del trigger es `Code in JavaScript7`, no `Code in JavaScript5`). Deriva `chat_id` directo de `message.chat.id` / `callback_query.message.chat.id` (sin duplicar el dispatch completo de `Code in JavaScript7`, que no hace falta para rate-limit) y si el evento es archivo (`message.document`/`photo`/`video`). Exención de admin: `chat_id === $env.DEFAULT_ADMIN_CHAT_ID` comparado como string en ambos lados (`_rl.exento`); también exento si no se puede derivar `chat_id` (`_rl.sinChatId`, caso borde).
- [x] 2.3 Insertados los nodos Redis `incr` (`Redis - RL incr msg corta/larga`, `Redis - RL incr file corta/larga`) con `expire: true` + `ttl` = largo de la ventana. **Hallazgo importante**: el nodo Redis de n8n (`incr`, ver `dist/nodes/Redis/Redis.node.js` del contenedor) NO condiciona el `EXPIRE` a que sea la primera incrementación — lo reaplica en cada llamada si `expire=true`. Esto NO es un problema acá porque el índice de ventana ya está embebido en el nombre de la clave (`m-<minuto>`/`h-<hora>`): cada ventana es una clave Redis distinta, así que "reaplicar TTL en cada incr" es idempotente dentro de la misma ventana y no crea una ventana deslizante. Se descarta entonces la necesidad de un IF que chequee `resultado === 1` o de un script Lua — el diseño de clave ya resuelve la condición de carrera que 2.3 anticipaba.
- [x] 2.4 Insertado el nodo IF `IF - RL dentro de cuota` — la comparación de los 4 contadores contra las cuotas (20/min, 200/hora `msg`; 5/min, 30/hora `file`) se resolvió en el Code node `Evaluar cuota rate limit` (más simple que 4 IFs numéricos encadenados); el IF solo lee el booleano `_rlEval.dentroDeCuota`.
